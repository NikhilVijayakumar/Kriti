# rust_dev — Dharma Domain System Proposal (Proposal 00)

## 0. Status

**Draft.** New proposal, not part of the closed 1-9 series (`docs/proposal/archive/{1..8,09}-rust_dev-*.md`) — those built and archived `samgraha/system/dev/rust_dev`, the Samgraha-facing standard. No schema, no code, no generator script — design only, per owner's ask ("can you create a proposal for this").

## 3. The real gap: one format, two representations, and a reference implementation already inside the tree

Samgraha's `rust_dev` and Dharma's Domain System model both describe "what sections/units a document needs and how to fill them" — for the 13 documentation domains they're currently expressed differently, but the target shape is not being imported from Bodha cold. `common/codegen/` (proposal 9) already runs the exact map/profile-default/profile split Bodha and Dharma proposal 05 call for, in the same repository:

| | 13 documentation domains (today) | `common/codegen/` code/test/build units (today, proposal 9) | Dharma Domain System (required) |
|---|---|---|---|
| Map (what units exist, hierarchy, required/generated) | Fused into markdown ToC + Template blocks + Required Sections table (three disagreeing views, §2) — **§5 resolves the actual parse source as a fourth input, the per-section deterministic audit YAML, not any of these three directly** | `{code,test,build}/map/*-map.yaml` — `units[]` with `id/title/parent_id/level/order/required/generated/profile/upstream/purpose` | `section-map.yaml` — `sections[]`, same fields plus `source` |
| Profile (how a unit is filled) | Also inside each Template block | `{code,test,build}/profile/*.yaml` + `profile-default/*.yaml` with `inheritance.allow_override`/`prohibit_override` | `section/profile/<key>.yaml` + `section/profile-default/<name>.yaml` |
| Fine-grained fill rules with severity/weight | `common/tier1/audit/deterministic/section/vision/*.yaml` — one file per section, `mandatory`/`severity`/`weight`/`evidence` per rule | `common/codegen/audit/deterministic/{code,test,build}/*.yaml` — same shape | `section/profile/<key>.yaml`'s `validation.rules` |
| Epic/Usecase/Task | `usecases:` list in `common/schema-manifest/standard.yaml`, flat; repo-state (`repo_new`/`repo_existing`/`repo_existing_no_doc`) has no structural level of its own — proposal 8 had to encode it into the usecase **name** (`propose-repo-new-tier{N}` vs `propose-repo-existing-tier{N}`), because Samgraha's model has nothing above Usecase to put it in | (not applicable — codegen units aren't usecases) | Epic → Usecase → Task → `task_step`, per `dharma/schema/mcp/{08-epic,09-usecase,10-task,11-task_step}.sql` and `docs/proposal/02-task-model.md` |

**This row is not a straight port.** Per owner direction: Samgraha's flat model is a *limitation* being routed around, not a shape to preserve. §5 ports the underlying spec — what Samgraha's repo-states and each domain's propose/audit/fix flow actually need to accomplish (per proposal 3, 5, 8's own text) — into Dharma's Epic level, which is exactly the structural slot Samgraha never had. Epic = repo-state (`repo-new`/`repo-existing`, two, not Samgraha's three — see §5 step 3 on why the no-doc case doesn't need its own Epic in Dharma), not tier.

This changes the shape of the work: `dharma/domain/system/dev/rust_dev`'s map/profile split for the 13 documentation domains should follow `common/codegen/`'s already-proven field names and `inheritance.allow_override`/`prohibit_override` conventions rather than Bodha's format read cold — Bodha and `common/codegen/` already agree closely enough that this is corroboration, not a conflict to resolve. (`common/codegen/`'s shared `profile-default` per unit-kind is one convention this design does *not* follow — see §4: every domain's sections carry their own profile, no shared default.) Proposal 05's "reuse over reinvention" holds either way; the reference implementation just makes the translation mechanical instead of speculative.

## 4. Proposed content-root layout

Section Map sits at a **shared level** (`domain/map/`, one file per domain), matching Bodha's `section/map/` and `common/codegen/`'s `code/map/` convention of a shared map folder rather than one nested per unit. Section Profile is nested per-domain (`domain/profile/<domain>/<section>.yaml`) — and, per owner decision (below), there is **no** Section Profile Default at all, shared or otherwise, unlike Bodha's `section/profile-default/` or `common/codegen/`'s `code/profile-default/`:

```
dharma/domain/system/dev/rust_dev/
├── domain/
│   ├── map/
│   │   ├── vision-map.yaml              # sections[], one file per domain (13 total)
│   │   ├── philosophy-map.yaml
│   │   └── ...
│   └── profile/
│       ├── vision/
│       │   ├── purpose.yaml             # filename = audit file's own snake_case section key, verbatim
│       │   ├── vision_statement.yaml    # NOT vision-statement.yaml — see note below
│       │   └── ...
│       └── philosophy/
│           └── ...
├── task.yaml                            # Epic → Usecase → Task → task_step tree — filename pinned by
│                                         # docs/proposal/08-schema-and-crate-architecture.md:136 and
│                                         # epic.sql/usecase.sql's own comments ("the task.yaml bundle
│                                         # this Epic was parsed from"), Bodha-crew task.yaml shape —
│                                         # NOT the invented `epic-usecase-task/rust-dev.yaml` path this
│                                         # proposal used before checking Dharma's own schema (see §5)
└── SYSTEM.md                            # carried over from samgraha/system/dev/rust_dev/SYSTEM.md, unmodified
```

**No shared `profile-default`, per owner direction: each domain's sections carry their own profile, full stop.** The prior revision proposed one shared `profile-default/rust-dev-standard.yaml` for the audit-contract shape + 25/25/25/25 weight split. Dropped: every `domain/profile/<domain>/<section>.yaml` is self-contained — `writing_objective`/`knowledge_goal`/`reader_goal`/`validation.rules` all live directly in that section's own file, nothing factored out to a shared layer. `section_profile.inherits` (`schema/mcp/07-section_profile.sql`) still defaults to Bodha's own `scientific-narrative` at the schema level — this design simply doesn't author a custom override for it, rather than authoring one and pointing every profile at it.

**Profile filenames are pinned to the audit file's own snake_case key, not kebab-case.** `domain/map/vision-map.yaml`'s per-section `profile:` field must equal the profile file's own key exactly (Bodha's contract: `profile: introduction` → `section/profile/introduction.yaml`, same name). The audit corpus's own keys are snake_case (`vision_statement`, `target_audience`, `guiding_principles`, `systems_vision` — read directly off the `common/tier1/audit/deterministic/section/vision/*.yaml` filenames). A generator emitting kebab-case profile filenames (`vision-statement.yaml`) while the map's `profile:` field carries the snake_case key verbatim would produce a dangling reference on every section. Pin snake_case throughout, sourced from the audit filename, not re-cased.

**Divergence from Bodha's pinned paths, named explicitly (not silently):** proposal 13 pins Bodha's actual paths as `section/map/section-map.yaml` (one file, all sections of one document type), `section/profile/`, `section/profile-default/` — a `section/` parent, singular map file per document type. This layout instead uses a `domain/` parent with `map/<domain>-map.yaml` (one file *per domain*, 13 total, not one file total) — because a single `section-map.yaml` cannot hold 13 domains' independent section trees the way Bodha's single research-paper document type needs only one. This is a deliberate divergence, not an oversight, but it is unverified against how Dharma's capture flow actually expects to walk a multi-domain provider — see §7.

**Resolved, per owner direction: `common/codegen/` is excluded, not projected.** `implementation`/`qa`/`build` are already ordinary Domains among the 13 (tier5/6/7 equivalents) and stay exactly that — plain Section Map/Profile domains like the other 10, nothing special. `common/codegen/`'s code/test/build map/profile-default/profile content does **not** get projected into this Domain System at all, in any form — including it would either duplicate `implementation`/`qa`/`build`'s own Section Map/Profile content or require inventing a second structural layer underneath a Domain, and this design sticks to one: Domain → Section Map → Section Profile, uniformly across all 13.

## 5. Derivation, not duplication

`samgraha/system/dev/rust_dev` stays the single source of truth, untouched. `dharma/domain/system/dev/rust_dev` is a **generated, re-derivable projection** of it — same relationship proposal 9 designed between planning docs and generated `.rs` code, and the same map/profile split `common/codegen/` already runs for code/test/build units (§3), minus the shared profile-default layer (§4, owner decision). Concretely, a (future, not-yet-built) generator would, per domain:

1. **Section Map source, resolved (not "ToC + Template blocks," which was underspecified):** `domain/map/<domain>-map.yaml`'s `sections[]` is derived from the **per-section deterministic audit YAML** (`common/tier{N}/audit/deterministic/section/<domain>/NN-<section>.yaml`) — one section entry per audit file, in its numeric order. This is the authoritative source, not the markdown ToC or Required Sections table, because the audit files already carry exactly the fields a Section Map/Profile split needs: `mandatory` → `required`, the rule set → `validation.rules`, `severity`/`weight` carried through unchanged. The map file also carries a map-level `validation{}` block (present in both proposal 13's Bodha reference and `code-map.yaml`) — generated, not authored: `hierarchy.max_level`/`ordering.unique_order_per_parent` from the audit file numbering itself, `structure.duplicate_ids`/`orphan_sections` from a straightforward scan of the audit corpus for that domain. Each section's `source`/`upstream` field (present in both proposal 13 and `code-map.yaml`) is the audit YAML's own path (`common/tier{N}/audit/deterministic/section/<domain>/NN-<section>.yaml`) — the traceable origin of that row, not left blank.
   **Orphan-section rule, required, not optional:** an audit file with no matching `### Template` block still gets a `sections[]` row — confirmed live, this is not hypothetical: 2 of 136 audit files across the full 13-domain corpus have no Template block at all (`common/tier2/audit/deterministic/section/architecture/10-operational_readiness.yaml`, `11-observability.yaml` — no "Operational Readiness"/"Observability" heading anywhere in `domain/05-architecture.md`). Rule: `id`/`order`/`required` come from the audit file as normal; `generated: true` is set (there is no authored markdown to generate *from*); the corresponding Section Profile is validation-only (see step 2's orphan case).
   **This cross-check is a hard preflight, not a soft note:** the first revision called a Template/Required-table/audit-file mismatch "a defect worth surfacing" — too weak, given `architecture`'s 2 orphans and `vision`'s `systems_vision`-omitted-from-Required-table gap are both confirmed, live disagreements, not edge cases to warn about. The generator must fail its run for a domain whose Template-block count, Required-Sections-row count, and audit-file count don't reconcile under this document's own orphan rule — not emit the domain anyway with a warning.
2. **Section Profile.** One `domain/profile/<domain>/<section>.yaml` per audit file (filename = the audit file's own snake_case key, per §4's pin). Field-by-field source, named precisely (the first revision's "drawn from `minimum_content`/`length_guidance`" was wrong — those are length *counts* ("1 paragraph", "concise"), not objectives):
   - `writing_objective` ← that section's **Writing Guidance** subsection (Tone/Voice/Do/Don't bullets) — the actual prose statement of intent, not the Template block's count fields.
   - `knowledge_goal` / `reader_goal` — **no source exists in the markdown for these today.** Declare them authored/minimal (a short generator-inserted placeholder, explicitly marked, not silently invented prose dressed up as if it were transcribed) until a human author fills them in per domain — same honesty proposal 9 §2 already models for `engineering.md`'s literal `(To be written by the domain expert.)`.
   - `validation.rules` ← the audit YAML's `rules[]`, carried through field-for-field (`condition`/`message`/`severity`/`weight`/`mandatory`/`evidence`).
   - **Orphan case** (the 2 architecture sections from step 1): no Template block exists, so `writing_objective`/`knowledge_goal`/`reader_goal` have nothing to derive from at all — these three fields are authored/minimal by construction, not merely "no source yet"; the profile is otherwise normal (`validation.rules` still comes from the audit file, which does exist).
3. **Epic/Usecase/Task — ports the spec, not the flat structure (owner direction: Samgraha's flat model is a limitation to route around, not a shape to preserve).** Checked directly against `dharma/schema/mcp/{08-epic,09-usecase,10-task,11-task_step}.sql` and `docs/proposal/02-task-model.md` — this is a 4-level hierarchy (Epic → Usecase → Task → `task_step`), and `task` rows require NOT NULL `input_contract_json`/`output_contract_json`/`acceptance_criteria_json` (≥1 entry in each of `happy_path`/`corner_case`/`edge_case`). None of that exists anywhere in Samgraha's `usecases:` list — so "port" here means re-expressing what proposals 3/5/8 actually specify each flow *does*, in Dharma's richer structure, not transforming Samgraha's flat list field-for-field.
   **Corrected in this revision: Dharma has no Tier entity at all — checked directly against `schema/mcp/05-domain.sql`, which gives `domain` only an *optional, free-text* `tier` column ("optional tier position," proposal 05's own wording), not a structural table or grouping level, and Epic groups Usecases by "domain-wide objective" (proposal 02) with no tier semantics anywhere.** The prior revision's "one Usecase per real tier (7)" under `repo_new`/`repo_existing`, and the `cross-tier` Epic name, both still imported Samgraha's tier1-8 structure into a model that has no such concept. Corrected below; this revision additionally folds in owner decisions on Epic naming, the no-doc case, and the Audit Subsystem question:
   - **Epic naming is kebab-case, matching every Dharma-side example** (`rust-dev-domain`, `documentation-management`, `rust-development`, `electron-development`) — not the prior revision's `snake_case`/mixed style. Epics below: `repo-new`, `repo-existing`, `document-maintenance`, `cross-domain`.
   - **Epic `repo-new`** (greenfield) — one Usecase **per domain (13)**, not per tier — Task = that domain's propose-then-execute flow within a newly-registering repo. Content ported from proposal 8's actual spec (§2-§6: repo-state scan, per-domain generate/audit/fix), not derived from Samgraha's `steps: []`, which never carried this content to derive from.
   - **Epic `repo-existing`** (brownfield) — same, 13 Usecases (one per domain), **plus one more: `bootstrap-readme`.** Owner correction to the prior revision: Samgraha's own model needed a *third*, separate repo-state (`repo_existing_no_doc`) because its workflow required a distinct case for "existing repo, no docs yet." Dharma's Task/Usecase model doesn't need that structural split — "existing repo, may or may not already have this domain's document" is one condition a Task handles internally (bootstrap first if absent, then proceed as normal), not a reason for a whole separate Epic. So `bootstrap-readme` becomes the 14th Usecase under `repo-existing` (used when a Task detects no docs exist), and the prior revision's `repo_existing_no_doc` Epic — along with its whole cross-Epic Usecase-sharing problem (`usecase.epic_id` being a single NOT NULL FK, `schema/mcp/09-usecase.sql`) — is **eliminated**, not solved: there's nothing left needing to share Usecases across two Epics once there are only two repo-state Epics instead of three.
   - **Epic `document-maintenance`** — the 52 `generate-document-`/`deterministic-audit-`/`semantic-audit-`/`fix-{domain}` usecases, repo-state-agnostic by nature (same content whether the target repo is new or existing) — already domain-scoped, not tier-scoped, so this Epic needed no correction.
   - **Epic `cross-domain`** — `calculate`, `render-report`, `render-charts` (3 usecases with no `domain:` field and no repo-state either, spanning every domain rather than being scoped to one).
   - **Audit/generation/report are ordinary Usecases and Tasks — no special category, per owner direction.** Considered (previous turn) routing Samgraha's audit YAML content into Dharma's dedicated Audit Subsystem tables (`audit_definition`/`audit_rule`/`audit_semantic`/`audit_calculation`/`audit_weights`/`audit_template`, `schema/mcp/20-25`) instead of plain Usecases. **Rejected:** everything is Epic → Usecase → Task, uniformly — `deterministic-audit-{domain}`, `semantic-audit-{domain}`, `generate-document-{domain}`, `fix-{domain}`, `render-report`, `render-charts` are each ordinary Usecases with their own Task (input/output contract + acceptance criteria), the same as any other unit of work. This also settles what the prior revision flagged as a missing content category: nothing is missing, because that category isn't used at all in this design.
   - **Collapsed, not carried forward:** proposal 5's generic `propose-tier{N}-{generation,audit,fix}` (21 usecases, tier-named but repo-state-agnostic) is Samgraha's own earlier, now-superseded-in-spirit attempt at this same propose flow, before proposal 8 added the repo-state split it actually needed — `standard.yaml` still carries both families side by side only because nothing in Samgraha ever deleted the older one (confirmed live: both are present). Porting proposal 8's resolved spec means the Dharma projection does **not** inherit that duplication as a second, parallel Epic/Usecase set — it has one propose model (`repo-new`/`repo-existing`), not two, and that one model is domain-scoped, not tier-scoped.
   - **The `domain` table's optional `tier` column is still usable, just not structurally:** each of the 13 projected Domain entries (§4) may carry Samgraha's `tiers.yaml` tier number as this free-text metadata field, purely for traceability back to Samgraha's own ordering — it plays no role in Epic, Usecase, or Task grouping anywhere in this design.
   - **Task content is real authoring work, not a mechanical derivation, and not optional-until-later:** every Usecase above needs at least one Task with a populated input/output contract and all three acceptance-criteria categories before it's a valid `task` row at all — there is no Samgraha source field to parse these from (confirmed: no contract, no acceptance criteria anywhere in `standard.yaml`). Per `docs/proposal/08-schema-and-crate-architecture.md`'s "Dharma Is Infrastructure, Not an Author" (Dharma never authors content; every row traces to a captured provider file) — **this authorship is unambiguously ours, the provider, done before capture, not Dharma's and not deferrable to post-registration.** This is the single largest remaining gap in this design, named explicitly rather than framed as "0 tasks today, matching Samgraha's `steps: []` state" (that framing, in the prior revision, wrongly implied parity with a valid Samgraha state — Dharma's own schema makes an empty Task set invalid, not merely incomplete).
   - `task_step` rows (one Task's ordered execution steps) each need `required_capability`, a NOT NULL FK into `agent_system_registry.concern` (`schema/mcp/11-task_step.sql`) — likely `rust-development`, which is not registered anywhere yet. `register_agent_system` (`name, concern, description, content_root, is_privileged_request` — `docs/proposal/14-mcp-tool-contract.md`) is the concrete tool that would do it; still a separate registration this proposal doesn't perform (see §7).

Writing the generator for the Map/Profile side (§5 steps 1-2) is out of scope for this proposal, same as proposal 9 deferred its own code generator. The Epic/Usecase/Task side above isn't a generator target at all in the same sense — it's authored content, ported from the proposal specs by a person (or an agent, later), not parsed out of existing files.

```toml
[domain_system]
name = "rust-dev-domain"

[repository.ignore]
patterns = [
    "**/node_modules/**",
    "**/.git/**",
    "**/target/**",

```

`root_dir` uses the same `${DHARMA_DOMAIN_CONTENT_DIR}` env-var convention `dharma/config.example/dharma-domain.toml` itself uses, rather than a literal path — consistent with that file being an example/template pattern, not a hardcoded one (the first draft's literal `"dharma/domain/system/dev/rust_dev"` was a cosmetic inconsistency, corrected here).

`section_map` is set to `"domain/map"` (a directory, one file per domain inside it), not a bare filename — the first revision left this at `"section-map.yaml"`, which matched no file anywhere in §4's actual layout once the Map moved to a shared, per-domain-file location. This value is still a guess, not a confirmed contract: see §7's divergence-from-Bodha item — if Dharma's capture flow only accepts a single `section_map` file per provider, both this value and §4's layout need revisiting together, not independently.

**`domains`/`domain_exclusion` — added deliberately, beyond the pinned example (which has neither field).** `dharma/config.example/dharma-domain.toml` doesn't carry this, and by the strict "content_root's directory listing is the domain set" reading, it doesn't strictly need to — Samgraha's own `domain`/`domain_exclusion` (`samgraha.toml`) exists because a Standard *extends a shared base at runtime* (`rust_dev` extends `base_dev`), which Dharma has no equivalent of. Owner direction: add it anyway, for a real, separate reason — during Kriti's own development/testing of this Domain System, registering or testing against a subset of the 13 domains is useful, and a domain may later be decided out of the Dharma workflow entirely. Mirrors `samgraha.toml`'s own `domain = []` / `domain_exclusion = []` shape, scoped to this provider's own domain set rather than Samgraha's cross-standard one.

Version starts at `0.1.0`, independent of `samgraha/system/dev/rust_dev/SYSTEM.md`'s own `1.0.0` — the Dharma projection is new and unverified; it isn't entitled to inherit Samgraha's maturity number just because the content originates there.
